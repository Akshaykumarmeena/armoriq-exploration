The map

Where ArmorIQ sits

Same policies, enforced at different points in an agent's path. Tap a card.

SDK (Python / TS)

tried ✓

Enforcement inside your own code. The agent's plan is captured and signed, then every tool call is checked against it.

Analogy: the manager sitting next to the employee's desk.

Intent Gateway

tried ✓

Change one base URL in your OpenAI / Anthropic / Gemini client. The gateway checks every tool call the model returns and strips blocked ones. Has a Monitor mode: see what would be blocked before turning it on.

Analogy: a security desk at the building entrance.

My run (free Gemini key, zero ArmorIQ code, same policy as the SDK):

record only: get_weather ✓ send_email ✓ enforce: get_weather ✓ send_email ✗ "Tool call "send_email" was blocked by policy: block:tools.default"

Worked exactly as the docs say. The smoothest product I tried.

ArmorTools (ArmorClaude…)

tried ✓

Plugins for coding assistants (Claude Code, Codex, Gemini CLI). A record of every action, and rules to allow, hold or block tools or lock a folder.

Analogy: a dashcam plus a seatbelt for your coding agent.

My run (Claude Code, sandbox folder with fake secrets):

/armorclaude:armor policy add allow Read and Grep and Glob, deny Write and Edit, hold Bash Write(hello.txt) ✗ ArmorClaude policy forbid: policy4 ls ⏸ held for approval, then ran

The Write was blocked even though it was in Claude's own signed plan: plan and policy are two separate checks. Only the human can confirm a policy; Claude can only propose one.

Rough edges: the block names policy4, not the rule; a terminal rule is only a proposal on the dashboard; and "deny Write" didn't stop a file write done through the shell (cat >> file).

Intent Container

read only

Enforcement down at the operating system: files, processes, network. Child processes inherit the limits. Available on NVIDIA OpenShell; Linux, Docker and Google Agent Substrate in preview.

Analogy: locks on every door inside the building, not just the entrance.

The journey

From sign-up to first "allowed"

Workarounds needed: 5

Signed up, created an API key

Smooth. The key was accepted: ArmorIQ signed my first plan.

Ran the docs quickstart as written

MCPInvocationException ... /invoke (HTTP 500): Internal Proxy Error

Allowed and blocked calls looked identical. The real reason was hidden: no agent registered.

Switched to the session API

ValueError: Tool "get_weather" is not namespaced as <MCP>__<action>

The docs example uses bare names. Renamed to weather-mcp__get_weather.

First real block

send_email -> BLOCK tool-not-in-plan

The core idea worked on the first honest try.

Registered an agent

url must be a URL address. url should not be empty

The wizard says manual agents don't need a URL, then the server demands one. Used the URL method with a placeholder.

Used the agent ID from the console

agent_unresolved: no registered agent matches '1e849d07-…'

The SDK wants the agent's name, not the ID the console shows.

Tried to attach a policy

At least one governed tool is required AttributeError: 'ArmorIQSession' object has no attribute 'client'

The agent had "no tools yet", and the SDK method to declare tools crashes on a typo. Wrote the rule by hand in YAML.

It works

get_weather -> ALLOWED allow:get_weather#0 send_email -> BLOCK tool-not-in-plan

Same key, same agent, same user. One allowed, one refused.

My 2-minute walkthrough

  1. "Authenticated doesn't mean aligned." The keys say who; ArmorIQ asks whether this action belongs to this task.
  2. Show hello_sdk.py: the plan has one step, get_weather.
  3. Run it: get_weather allowed by rule allow:get_weather#0; send_email blocked as tool-not-in-plan.
  4. Point out it's fail-closed: when ArmorIQ isn't sure (unknown agent, no policy), the answer is no.
  5. "Getting here took five workarounds. Here's the list, and here's the one-line fix I'd start with."
